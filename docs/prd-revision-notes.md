# PRD revision notes (for the owner)

The implementation follows the PRD except where the PRD cannot be met as written. These are the edits the owner should make to `cd project prd.docx`, each with the evidence.

1. **F2 acceptance wording and the metric set.**
   - Replace "a file with one missing semicolon that previously produced 10 or more errors shows 1 root cause". With phrase-level recovery a missing `;` yields 1 raw record, so there is nothing to cluster (`docs/error-recovery.md` section 10).
   - Replacement: (a) a file with one missing semicolon shows exactly 1 root, SYN-MISSING-SEMICOLON, right after the unterminated statement; (b) for every single-fault file in the cascade set, the displayed count is 1 and the root is the injected fault; (c) report raw vs displayed summed over the cascade set, with the per-file table.
   - Define the metric: the cascade set is the programs whose hand-traced raw count is at least 2. The "at least 70% fewer" target is measured on the single-fault cascading files; the all-cascade figure (which includes multi-fault files) is reported next to it. Warning roots count as displayed.
   - Say how the target is judged on held-out data. A 2-raw to 1-shown file is only a 50% reduction, so the percentage depends on how many tiny cascades the set contains. The owner should decide whether to keep 70% or restate it (for example "at least 60% on all cascading files, and exactly 1 root for every single-fault file"). Held-out result: see `docs/evaluation/evaluation.md`.
2. **F3 vs F8 contradiction.** F3 says "every root error has an explanation and a diff" and Suggest fix "returns a diff view"; F8 says "no unverified fix is ever displayed as a fix" and that after 3 failures only an explanation is shown. Both cannot hold. Implemented: F8 wins. F3's acceptance should read "every root error has an explanation; a diff is shown only when verified (F8)". Raw model patches are never displayed.
3. **Error record schema: add `message`.** F1 lists "message" among the record's contents but the schema table omits it. Also added: `language` (always `"c"`), `caused_by` and `span_end`. `root_id` is the record's own id for roots; `caused_by` is null when no cause is known.
4. **RAG: a keyed index, not Chroma.** The tech stack names Chroma with sentence-transformers embeddings. The corpus is small (one chunk per grammar/semantic rule plus one fix pattern per catalog code) and retrieval is already keyed on phase, error code and rule_ref (F7's own wording), so a deterministic lookup is exact, needs no model download and is testable offline. Chroma and embeddings would add a heavy dependency and nondeterminism for no accuracy gain at this size. State this and mark Chroma optional.
5. **Privacy note.** The PRD says only the error context goes to the LLM. Be precise: the error record, a few source lines (the whole source for a fix request), the matched rule text and the verbosity mode are sent; the filename, paths and student ID are never sent (tested). Code snippets do go to the provider (Gemini free tier) unless the local Ollama model is used, and free-tier providers may use submitted content. The consent text in `docs/evaluation/user-study.md` says this.
6. **Latency definition.** "Under 5 seconds for default explanation" needs a definition: the time from calling the agent for one root error (default = short, beginner) to receiving the text, with a cold explanation cache, over 50 requests, reported as median and p90, for a named model on named hardware. State that a cache hit is near-instant and excluded from the target, and that a local 8B model on a laptop GPU and a hosted free-tier model differ widely. Define the F8 time budget separately (10 s in the product; the evaluation used a longer budget and reports how many fixes would have fitted in 10 s).
7. **Smaller points.** F9: say that a category is counted once per root per compile and an error signature once per session. F8: define "fixable" (here: the sidecar flag plus a fatal root; the unit is the first fatal root). The success-metric row "Run the verifier on the same 20 programs" mixes dev and held-out data; say which split is the reported one and that the other is for development.
